# Demo Section 7: Pros, Cons & Limitations (2 min)

Owner: Member 1 (Sarah Rae).

**One-sentence version:** Letting ARC and `InputStream` do the work gave us a program whose memory behaviour is observable and deterministic enough to *prove* things on stage, at the cost of hiding the allocator underneath, and most of what we show is reasoning about one machine rather than measurement of all of them.

---

## 1. Pros of our approach

- **Determinism makes the demo provable.** ARC frees an object the instant its strong count reaches 0, so a `deinit` line lands at an exact, repeatable point in the output. In a garbage-collected language the same demo would print "eventually," and the retain-cycle section would have nothing to show.
- **The leak is visible as silence.** The leaky and fixed versions are the same shape with one keyword different, so the only variable is `weak`. Missing `deinit` lines are evidence anyone can check without a tool.
- **One reused buffer makes capacity vs. count concrete.** Printing the same storage address on every chunk shows one allocation being refilled, rather than asking the audience to take it on trust.
- **Song sizes were chosen as test cases, not arbitrarily.** 10,000 / 8,192 / 100 bytes against a 4096 buffer cover partial, exact-fit and smaller-than-buffer. The 8,192 case is the one that *hides* a stale-buffer bug — the buggy version's checksum still matches — so the suite catches a bug the obvious test misses.
- **Checksums make correctness a measurement.** Bytes played == file size and checksum(played) == checksum(original) are verified every run, so "the buffer logic is right" is a number rather than an assertion.
- **Five files, five owners, one module.** Everyone's code sees the shared models with no imports, and nobody edited anyone else's file.

## 2. Cons

- **ARC's cost is invisible in our output.** Retain/release traffic is real work the compiler inserted, and we never measure it. A program that passes objects around heavily pays for it, and nothing we print would reveal that.
- **`weak` is not free either.** Weak references need side-table bookkeeping so they can be zeroed when the target dies. We present `weak` as simply "the fix" and never price it.
- **We demonstrate exactly one heap risk.** A retain cycle is the clearest Swift leak, but not the only memory problem: unbounded caches, oversized buffers held too long, and closures capturing `self` are all more common in practice, and a cycle through a *closure* is far more common than our delegate cycle.
- **`DemoLog`'s mutable global is a compromise.** `deinit` takes no arguments, so a section label has to live somewhere global, and Swift 6 requires `nonisolated(unsafe)` to allow it. That is honest in a single-threaded program and would be a real data race the moment anyone added a thread.
- **The buffer size is fixed at 4096 and never justified by measurement.** We picked a conventional number; we never tested whether 1 KB or 64 KB performs differently, so we cannot claim 4096 is a good choice — only a defensible one.
- **Reading with `InputStream` hides a layer.** Our chunk count measures calls we made into Foundation, not reads that reached the disk. The file system cache and any buffering inside `InputStream` sit underneath, so "3 chunks" is 3 reads *by our code*, not 3 trips to storage.

## 3. Limitations of our results

- **The comparison runs on one Mac, and that is not a presentation flaw but a requirement.** Array growth is a standard-library implementation detail with no promised growth factor, and the team's toolchains are not identical. Numbers from two machines are not a comparison; `docs/machine-details.md` records which Mac produced the report's figures.
- **Debug vs. release changes what we are even looking at.** All measurements use `-c release`, because a debug build leaves the optimiser off. The flip side: the stack demo runs in *debug* precisely so the call stack matches the source, since an optimiser is free to inline or flatten recursive calls. Depth in our output is the source's depth, not necessarily the depth an optimised build would use.
- **`deinit` output proves release, not reclamation.** It shows ARC freed the object. It says nothing about whether libmalloc returned the block to macOS, and usually it did not.
- **Process-level numbers move in pages, not objects.** `/usr/bin/time -l` max RSS is whole-process and page-granular (16 KB on Apple Silicon), so small allocations may not move it at all. It cannot be used to confirm an object-level claim.
- **Peak-memory claims are inferred, not measured.** We reason that appending without reserving holds old and new storage simultaneously during each regrowth. We never sampled memory *during* a copy to watch the spike. The reallocation count is measured; the peak is an inference, and the report labels it that way.
- **Simulated audio.** Songs are files of generated bytes. Nothing here is affected by real decoding, variable bitrates, or network delivery, all of which dominate a real streamer's memory behaviour.
- **Single-threaded throughout.** Project 1 covered concurrency; this program deliberately has none, so nothing we show accounts for allocator contention between threads, which is a real cost in production systems.
- **Small sample sizes.** Five runs per approach is enough to show a difference that is large and consistent; it is not enough to make a claim about a small one.

## 4. Improvement we would make with more time: memory-mapped reading

Add a third strategy to the buffer comparison — map the file into the address space instead of copying it through a buffer:

```swift
let data = try Data(contentsOf: url, options: .mappedIfSafe)
```

**Why this one, out of everything we could add.** It is the only option that puts a *fourth* actor on stage. Our current demo has our code, ARC and libmalloc; memory mapping hands the job to the **kernel**, which maps file pages into the process and faults them in on demand. Suddenly the 16 KB page size from `machine-details.md` stops being trivia and becomes the mechanism — the unit the data actually arrives in.

It would also sharpen every claim in the buffer section by contrast:
- RSS would rise with the file size while *our* allocation count stayed flat, separating "memory we allocated" from "memory the process is using" more clearly than anything we currently show
- it makes the chunked approach's real advantage explicit — bounded, predictable memory we control — rather than letting it look strictly better
- it gives an honest case where our approach *loses*: for random access across a large file, mapping is simpler and faster

**Why we did not do it:** it needs a file large enough for paging to be observable (hundreds of MB), which pushes past the input sizes the rest of the demo uses, and it would need its own measurement methodology to be worth claiming anything about.

## 5. Practice-question answers for this section

**"What's one limitation of your implementation?"**
Pick the sharpest: our peak-memory claim is inferred, not measured. We count reallocations directly, but we never sampled memory during a copy to watch old and new storage coexist. We label it inferred in the report rather than implying we watched it happen.

**"What would you do differently?"**
Memory-map the file as a third strategy, because it brings the kernel into a demo that currently stops at libmalloc, and it would give us a case where chunked buffering is the wrong tool.

**"Is your comparison fair?"**
Both approaches do identical work on identical input and we assert `samplesA == samplesB` before reporting anything. It is fair as a comparison of those two approaches on one machine and one toolchain. It is not a general claim about Swift arrays, because the growth behaviour we measured is unspecified and may differ across versions.
